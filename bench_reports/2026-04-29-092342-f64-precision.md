### 3. Root cause: SharedBlockCache race-dependent content

The DashMap block cache (`src/io/readers/block_cache.rs`) has a "first 500 blocks win,
then skip all new inserts" policy. With `Ordering::Relaxed` atomics, which 500 blocks
get cached depends on the thread scheduling race during the first few hundred batches.

The f64 change alters batch processing timing:
- 2x larger coverage buffers → slightly different per-batch duration
- Different thread interleaving → different blocks win the 500-slot race
- Frequently-accessed blocks that won in f32 may lose in f64
- Every cache miss → full zlib decompression of a ~64KB block

**Evidence:**
- `BigWigReader::values` became the #1 allocation source (3,587,268 calls vs
  absent from baseline top sources) — confirming more cache misses
- zlib decompression time increased 2.6x — consistent with ~2.6x more block
  decompressions
- Allocation calls up 26% — extra allocs from `read_and_decompress`

### 6. Required fix: Block cache eviction policy

The current "skip when full" policy is fundamentally broken for variable-timing workloads.
Options:
- **LRU eviction** (replace least recently used when full) — deterministic behavior
- **Size-based cap** (e.g. 256 MB) instead of entry count — adapts to block sizes
- **Per-thread caches** with global deduplication — eliminates DashMap contention

This is a pre-existing design limitation exposed by the f64 timing change.

### 7. Verdict

**FAIL** — regression >5% (wall clock +62%, task-clock +90%)

However, the regression is NOT caused by the f64 type change itself (application code
regresses < 6%). It is caused by the SharedBlockCache's race-dependent "first 500 win"
policy producing a worse cache content set under the altered thread timing. **Fixing the
cache eviction policy is expected to restore baseline-comparable performance.**
